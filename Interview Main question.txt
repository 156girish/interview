		JWT flow :

		The flow is: the client posts username/password to a login endpoint which authenticates using the AuthenticationManager (via UsernamePasswordAuthenticationFilter or a login controller). On success the server issues a JWT and returns it. For every subsequent request the client sends Authorization: Bearer <token>. A OncePerRequestFilter (the JWT filter) — added before UsernamePasswordAuthenticationFilter — extracts and validates the token (signature + expiry), maps claims to GrantedAuthoritys, and sets an Authentication into SecurityContextHolder. The app should use sessionManagement().sessionCreationPolicy(SessionCreationPolicy.STATELESS), have proper AuthenticationEntryPoint/AccessDeniedHandler, and a secure refresh-token strategy for production.

		If they ask “If it’s stateless, where/how is the token stored?” answer briefly:

		Stateless means the server does not persist the token — the client stores it and sends it with each request (usually in Authorization: Bearer <token>). Best practice: keep short-lived access tokens in memory and store long-lived refresh tokens in an HttpOnly; Secure; SameSite cookie (server sets it). Use HTTPS, rotate keys, and keep refresh-token state server-side if you need revocation.

		Quick bullets to mention if they probe further:

		- Add the JWT filter with http.addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class).
		- Set SessionCreationPolicy.STATELESS for JWT APIs.
		- Use PasswordEncoder + AuthenticationProvider and an AuthenticationManager for login.
		- Implement AuthenticationEntryPoint and AccessDeniedHandler for 401/403 responses.
		- Validate signature, expiry, and optionally jti for revocation; consider refresh tokens for UX.
		- Store refresh tokens in HttpOnly cookies and rotate/blacklist them in DB/Redis if you need logout/revocation.

		interface vs Abstract


		1. What happens if we don’t implement all methods of an interface?

		If a class implements an interface but does not provide implementations for all of its abstract methods,
		then that class must be declared as abstract.

		Otherwise, the compiler will throw an error — because a non-abstract class must fully implement all the methods of its interface.

		Because interfaces define a contract.
		Any concrete class (non-abstract class) that claims to implement that contract must fulfill all the methods,
		otherwise it breaks the contract.

		2. Can we use an abstract class as a normal class (i.e., without subclassing it)?

		❌ No, you cannot instantiate (create an object of) an abstract class directly.
		But ✅ you can use it in other ways — for example, as a reference type or by creating an anonymous subclass.

		3. What if two interfaces have methods with the same signature?

					If two interfaces have methods with the same method signature (same name and parameters),
					then the implementing class needs to provide only one implementation — it will satisfy both interfaces.

					interface A {
						void show();
					}

					interface B {
						void show();
					}

					class Demo implements A, B {
						public void show() {
							System.out.println("Show method implementation");
						}
					}

					***If the return types differ, the compiler will throw an error.
					***If two interfaces have default methods with the same signature,
					   then the implementing class must override the method to resolve the ambiguity.
					   
					interface A {
						default void show() {
							System.out.println("A show");
						}
					}

					interface B {
						default void show() {
							System.out.println("B show");
						}
					}

					class Demo implements A, B {
						public void show() { // 👈 Must override to resolve conflict
							System.out.println("Demo show");
						}
					}

					*** Two methods with the same name and parameters but different return types are incompatible.

					The super keyword (like A.super.show()) works only for default methods (i.e., methods with a body) in interfaces —
					not for abstract methods.

		4. Can we mark an abstract class as final? Can we declare an interface as final?
		❌ No. Because final prevents inheritance, and abstract classes are meant to be inherited.
		❌ No. Interfaces are meant to be implemented.

		5. Why do we need interfaces when abstract classes exist?

		Interfaces support multiple inheritance, loose coupling, and flexibility in design — for example, a class can extend another class and implement multiple interfaces.

		prototyp scope example : A shopping cart in an e-commerce app.

		@Scope("prototype") → creates a new bean every time you call context.getBean().

		@Scope("singleton") (default) → returns the same bean each time.

			Yes, prototype creates a new instance per request, but this "request" means a request to the Spring container, not HTTP requests.

				@Component

					@Autowired
					private B b; // B is prototype
				}

				@Component
				class C {
					@Autowired
					private B b; // B is prototype
				}

				When Spring creates bean A, it injects one instance of B into A.

				When Spring creates bean C, it injects another instance of B into C.

			They are created every time the bean is requested from Spring.

			Injection happens only once → so you only get one prototype instance per injection.

		✅ Request Scope

			A new bean instance is created for every HTTP request (only valid in web applications).

			The bean lives only during that HTTP request.

			After the request is completed, the bean is destroyed.

			Prototype → Per getBean() call

			Request → Per HTTP request

		Rest API :

		1. What is a REST API?

			REST (Representational State Transfer) is an architectural style that allows systems to communicate over HTTP using standard methods like GET, POST, PUT, DELETE.
			It treats everything as a resource identified by a unique URI (Uniform Resource Identifier).
			
		⚙️ 2. What is a REST Controller in Spring Boot?

			@RestController = @Controller + @ResponseBody
			It automatically serializes Java objects to JSON responses.


		Key Points Interviewers Look For 

			***An idempotent REST API means that multiple identical requests have the same impact as one

			POST is non-idempotent (calling twice → creates two records).

			PUT is idempotent (calling twice → same result, resource replaced).

			PATCH is non-idempotent and for partial updates.

			DELETE should ideally be idempotent.

			GET requests should not change the server state (should be safe).
			
			
		Q1. Why is PUT considered idempotent but POST is not?

			Answer:

			PUT → Replaces the entire resource.
			If you send the same PUT request multiple times, the state remains the same.

			POST → Creates new resource each time (can generate new IDs), so multiple calls create duplicates.

		🔹 Q2. What’s the difference between PUT and PATCH?

			Answer:

			PUT replaces the entire resource.

			PATCH updates only specific fields.

		🔹 Q8. If you send POST twice accidentally, what happens?

			Answer:
			Two separate resources may be created (not idempotent).
			That’s why APIs should return unique IDs and support idempotency keys for payment systems (like Stripe).


		🔹 Q13. Can PUT create a new resource?

			Answer:
			Yes — if the resource with given ID does not exist, PUT can create it.
			But this behavior should be clearly defined in the API design.

			class Test {

					System.out.println("First static block");
				}
				static {
					System.out.println("Second static block");
				}
			}

			✅ Answer:
			All static blocks execute in the order they appear, only once, when the class loads.

		❓Q2. Can a class have both static block and constructor?

			✅ Yes.
			The static block runs first (during class loading), then constructor runs (during object creation).

		❓Q3. Can we access non-static variables in static block?

			❌ No.
			Static blocks can only access static members directly because non-static variables belong to an instance.

		❓Q4. Can static block throw checked exception?

			❌ No, unless you handle it inside try-catch, because class loading can’t propagate checked exceptions.

		❓Q5. Can we call a constructor from a static block?

			✅ Yes, you can create an object inside a static block:

			class Test {
				static {
					Test t = new Test();
					System.out.println("Object created in static block");
				}
				Test() {
					System.out.println("Constructor executed");
				}
			}


			Output:

			Constructor executed
			Object created in static block

		❓Q6. Can we make constructor static?

			❌ No.
			Because constructors are meant for instance creation, not for class-level operations.

		❓Q7. Can we call one constructor from another?

			✅ Yes, using this() keyword (for constructor chaining).
			✅ Constructor Under Constructor = Constructor Chaining

			Java allows you to call one constructor inside another using the keyword:
			this() → calls another constructor of the same class
			super() → calls parent class constructor

		✅ 1. Global Exception Handler works in the Controller Layer

		@ControllerAdvice / @RestControllerAdvice is designed to handle exceptions thrown by controllers or anything below controllers (Service, DAO).

		Meaning:

			DAO throws exception → goes to Service

			Service throws or rethrows exception → goes to Controller

			Controller doesn’t handle → GlobalExceptionHandler catches it

			So yes, GlobalExceptionHandler works only at the top — Controller/API layer.

		🟦 But can we handle exceptions in other layers?

			Yes, but differently:

			✔ DAO Layer

			Wrap low-level exceptions into custom exceptions and rethrow.

			✔ Service Layer

			Catch DAO exceptions and either:

			Handle (business logic),

			OR wrap into a new Service-level exception,

			OR rethrow to be caught by Controller.

			❌ You should NOT handle API responses in DAO or Service layer.

			Only Controller layer should convert exceptions into HTTP responses.

		🟩 2. Best Practice Flow (Enterprise Pattern)
			DAO → throws DataAccessException
			Service → catches & wraps → throws ServiceException
			Controller → Global Handler converts to HTTP response


		Example:

			DAO:
			catch(SQLException e) {
				throw new DataAccessException("DB error", e);
			}

			Service:
			catch(DataAccessException e) {
				throw new ServiceException("Service failed", e);
			}

			Controller Advice:
			@ExceptionHandler(ServiceException.class)
			public ResponseEntity<?> handle(ServiceException ex) {
				return ResponseEntity.status(500).body(ex.getMessage());
			}

		⭐ Key Rule (Interview Ready)

			DAO and Service layers should throw exceptions upward, but the actual handling (for end-user response) must be done at the Controller level — ideally in a GlobalExceptionHandler.

			This is the cleanest architecture.

		🟡 Summary
			Layer	Should Catch?	Should Handle?	Should Throw?
			DAO	Yes	No	Yes (wrap & throw)
			Service	Yes	Maybe	Yes (wrap & throw)
			Controller	No	No	Let Global Handler catch
			Global Exception Handler (@ControllerAdvice)	Yes	Yes	Converts to HTTP response

		🎯 Correct Flow 

			DAO Exception → wrap into DAO_CustomException → throw
			Service Layer → catch → wrap into Service_CustomException → throw
			Controller → nothing (let it bubble up)
			GlobalExceptionHandler → catches & returns proper HTTP JSON response

		✅ If a REST API (GET endpoint) receives 100 requests, how many controller instances are created?
		✔ ONLY ONE INSTANCE

			Spring creates only one object of your Controller (by default).
			This single instance will serve all 100 requests — one at a time or concurrently depending on thread pool.

		🧠 Why?

			Because:

			▶ Spring beans are singleton by default

			@RestController → @Controller + @ResponseBody
			And @Controller is a singleton-scoped bean unless changed.

			So:

			1 controller instance per application

			The same instance is reused for every incoming HTTP request

		🍃 Spring Boot Thread Model

			Even though there is one controller object,
			multiple threads handle requests.

			So:

			100 requests → 100 threads (from Tomcat thread pool)
			BUT → all threads call the SAME controller instance

		⚠ Important Note

			Since a controller is singleton:

			Do NOT use instance variables that change per request
			(because multiple threads may modify them simultaneously)

			Example of bad code:

			@RestController
			public class MyController {
				private int counter = 0; // ❌ dangerous

				@GetMapping("/test")
				public int test() {
					return ++counter;  // race condition!
				}
			}


			Controllers should be stateless.

		🟩 Summary (Interview Answer)

			Spring creates only one instance of a @RestController (because it is a singleton bean).
			Even if 100 or 10,000 requests come, the same instance is used.
			Multiple threads access this controller instance, so controllers must be stateless.

		🚀 What is a Parallel Stream?

			A parallel stream processes data using multiple threads at the same time instead of a single thread.

			It uses the Fork/Join framework internally to split the task into smaller chunks, process them in parallel, and then combine the results.
			
		🔥 How Parallel Stream Works (Internally)

			List → split → process in parallel threads → combine → final result

		🎯 Interview-Friendly Explanation

			“Parallel streams use the ForkJoin Framework.
			When we call .parallelStream(), Java splits the collection into multiple chunks using a Spliterator.
			Each chunk is processed by different threads from ForkJoinPool.commonPool.
			After processing, results are combined and returned.
			It improves performance for CPU-bound tasks on large datasets.”

		❓ If all connections are used, what can we do?

		✅ 1. Increase max pool size (MOST COMMON FIX)

			If your application handles many parallel DB calls:

			maximumPoolSize = 10 or 20

			This allows more concurrent DB operations.

			But…
			⚠️ Only do this if your DB server can handle the load.
			Otherwise you push load onto DB, causing crashes.

		✅ 2. Reduce the number of DB calls

			If your API hits DB multiple times, reduce them:

			✔ Combine multiple queries
			✔ Use joins
			✔ Use batch operations
			✔ Avoid unnecessary fetches
			✔ Use pagination

			Example:
			Instead of calling DB 10 times:

			SELECT ... WHERE id IN (1,2,3,4)


			One single query.

		✅ 3. Add Caching (Redis / In-memory)

			If data is frequently read and rarely updated:

			✔ Cache DB results
			✔ Serve responses from cache
			✔ Reduce DB load
			✔ Free up connection pool

			This is one of the best long-term fixes.

		✅ 4. Reduce Connection Hold Time

			Sometimes connection pool exhaustion happens not because of high traffic but because:

			❌ A query is slow
			❌ Transaction takes too long
			❌ Code is blocking
			❌ Prepared statement not closed

			Fix by:

			✔ Optimizing SQL
			✔ Adding proper indexes
			✔ Reducing transaction scope
			✔ Moving long operations outside DB

		✅ 5. Add a Queue / Async Processing

			If too many requests hit at the same time:

			✔ Process them async
			✔ Put heavy DB tasks into queues (Kafka, RabbitMQ)
			✔ API responds fast, processing happens later

		🚨 BONUS — If connection pool is exhausted, Spring Boot logs this:
		HikariPool-1 - Connection is not available, request timed out after 30000ms


		This is a strong indicator that your DB or pool size is insufficient.

		🎯 Final Interview-Ready Answer

		“What happens if all DB connections are in use? What would you do?”

			Otherwise, we optimize DB calls, add caching, reduce slow queries, or use async processing to reduce pressure on the DB.
			The goal is to reduce the time a connection stays busy and minimize DB round trips.”

3. how dependency injection works in Spring, and why it’s beneficial in building enterprise applications.

"In Spring, beans are created when classes are annotated with @Component, @Service, or @Repository. These beans are stored in the IoC (Inversion of Control) container, also known as the Application Context. To use these beans, we inject them into other classes by using the @Autowired annotation. This allows Spring to supply the right bean from the container directly into our fields, constructors, or setters. This approach removes manual instantiation, making our code more modular, easier to test, and easier to maintain."

5. What’s the difference between using a blocking REST client like RestTemplate and a non-blocking one like WebClient in Spring?"

"RestTemplate is a synchronous, blocking client. When you call an API with it, the thread waits until the response arrives before continuing. WebClient, on the other hand, is asynchronous and non-blocking. It uses reactive streams, returning types like Mono or Flux, so you can handle data when it’s ready, without tying up threads. WebClient is more efficient for high-concurrency use cases, while RestTemplate is simpler but suited for synchronous workflows."
